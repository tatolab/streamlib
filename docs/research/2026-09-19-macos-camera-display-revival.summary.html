Getting StreamLib working on macOS again

Target: camera live in a window on Apple Silicon, with the scaffolded app — including its Python effect — working exactly as it does on Linux.

Everything checks out. The design you want is the one the hardware supports. Keeping Vulkan on macOS isn't a compromise — it's the cheap path. MoltenVK gives a Vulkan 1.3 device that accepts every feature the engine demands, presents through a CAMetalLayer, and imports an IOSurface as a VkImage with no copy.

Cross-process GPU frames work, the ordering contract survives intact, and the last open question is now closed — the timeline crosses to a spawned child using only public API, with no launchd service and no bundle. And there's a runnable sample app: a real Python child editing a real 1080p GPU frame through numpy, verified pixel-exact over 300 frames, at 698 fps.

The engine doesn't compile for macOS today. But not one of its 65 errors is a MoltenVK limitation — they're an unapplied Rust edition migration, a stale second GPU backend, and #[cfg(linux)] on code with nothing Linux in it.

The cross-process story — yes, you're good

Your framing is right and it's also what the tree already does: the Mach channel only exchanges handles. iceoryx2 stays the data plane. That split isn't new work — it's the existing architecture.

Per frame
a bag carrying a surface id string over iceoryx2. No handle, no fd, no port.
Per pool slot, once
the producer registers the buffer, a consumer checks it out — that is where the fd (Linux) or Mach port (macOS) crosses.
Verified
register_buffer is called from the pool's pre-allocation loop, once per slot. Nothing per-frame touches it.

So the Mach channel is a low-frequency control path — touched a couple of dozen times at setup, then effectively never. Transport latency is irrelevant (I measured ~4 µs anyway, on par with a Unix socket). The per-frame cost on macOS is iceoryx2, plus an already-imported per-slot-cached VkImage, plus a timeline wait. The pre-iceoryx2 design pushed frame data through this channel; nothing does now.

One correction: the mechanism is raw Mach, not XPC

Your instinct about no service install is exactly right — that outcome is fully achieved. But anonymous XPC can't reach a process that doesn't exist yet: an XPC endpoint cannot be serialised to bytes (it throws "may only be encoded by an NSXPCCoder"), so it can only travel over an XPC channel that already exists. Circular. The service-less mechanism that actually works is raw Mach — which also hands you the public audit token and dead-peer notifications that XPC makes harder to get.

✓ The open question — resolved

The last unknown was how the Metal shared event (the timeline) reaches a child without a launchd-backed XPC service. It can, using only public API. NSXPCCoder is a public Foundation class, and MTLSharedEventHandle checks only that the coder is one — it never looks at the connection, which is nil in a subclass. So a coder subclass extracts the handle's Mach send right, which crosses the channel the IOSurface already uses. Proven: 500 device-side cross-process round trips at 120 µs each, with the 1080p data path verified pixel-exact alongside it.

Public API, but used in a way Apple doesn't document — rate it ~7/10 durable and keep the fallback wired behind the same interface. What's load-bearing isn't the API, it's the encoded shape (one Mach send right plus a label). Failure is safe — a bad port returns nil, not a crash — so the swap can be a runtime fallback. And the fallback is cheap: host-side ordering costs +26–100 µs per frame, under 1% of a 16.7 ms budget. Neither outcome threatens the milestone.

⚠ One hard rule that came out of it

A committed command buffer whose GPU wait isn't satisfied within ~5 seconds is killed by the OS, and MoltenVK marks the whole VkDevice lost — unrecoverable. The spike hit this for real when its child blocked on a full socket. A wedged Python helper must never be able to take the engine's device down. So: never let the producer GPU-wait on a consumer that can stall; bound it host-side with a watchdog well under 5 s. That's a design rule for the ticket, not implementer's discretion.

The CPU path is better than Linux

Linux reads write-combined memory at ~175 MB/s, which is why the scaffolded effect does a bulk copy instead of editing in place. On Apple Silicon the default IOSurface mapping is cached and reads at heap speed — ~50 GB/s. That performance workaround is unnecessary here (and the comment explaining it will read as wrong on a Mac).

Why it's broken right now

Three months of Apple code, then seven months of nobody compiling it. All 12 CI jobs run on Ubuntu; even the source-linting tools skip the Apple files on purpose. So it rotted silently.

Where Apple's SDKs earn their place

One RHI — Vulkan — everywhere. Apple frameworks at the edges only:

  • AVFoundation for capture → hands off an IOSurface to Vulkan
  • AppKit / CAMetalLayer for the window → hands off a VkSurfaceKHR
  • IOSurface + Mach ports for cross-process frames; MTLSharedEvent for the ordering
  • VideoToolbox for codecs later — MoltenVK has no Vulkan Video at all
  • CoreAudio later, behind the audio backend trait that already exists
  • mach_absolute_time for the clock — already shipped and correct

Decisions — all resolved

All five open questions were settled by the owner on 19 Sep 2026, plus two recorded rather than asked. They are written into docs/plan/changes/macos-platform-floor.md with their consequences.

✓ Supported floor, not a developer machine
"I want people to be able to build and run it, not just develop on it." §Product names Apple Silicon, CI gates macOS on every PR, the wheel is in the release closure, and a macOS-only regression blocks a release. This is what makes capture, present, cross-process frames and the wheel part of the milestone rather than optional.
✓ One Vulkan RHI; src/metal/ deletes
MoltenVK is the macOS driver. No behavioural change on Linux — backend-metal was never in default — but six shared core/rhi files have their cfg expressions edited, so Linux CI green is a proof obligation.
✓ Bootstrap-name rendezvous now; posix_spawn later
No Linux impact from the choice taken. The posix_spawn restructure becomes its own change with its own Linux proof, because python_helper_process_spawn_host.rs is one shared file — that change would alter the spawn path on both platforms.
✓ conditional · Camera carries the capture instant
The one entry that is not additive — it alters Linux behaviour. Gated on a Linux regression check covering audio sync, encoder PTS, Mp4Sink, the mesh and loss metrics. Tickets can be derived, but the timestamp work must not merge until that check reports; if it finds a consumer this breaks, the decision reopens.
✓ arm64 only — no Intel, no Rosetta
One wheel, one CI lane. With a direction attached: optimise for modern Apple Silicon and take the newest capability available rather than the most compatible. That bites the deployment-target choice, and raises KosmicKrisp from curiosity to a real evaluation once a macOS 26 floor is acceptable.
✓ Recorded, not asked
Cross-process frames are in scope, not deferred. And the artifact is the wheel, identical to Linux — no .app bundle, no launchd, no installer, under any justification. That retired two fallbacks this research had left open: the .app re-exec for the terminal-permission edge case, and a bundled XPC service for the shared-event seam.

Risks worth carrying

  • ~0.5 s Vulkan device bring-up per process. Measured. Every Python helper pays it, and there's a test pinning the helper startup budget. Warm it before the real-time loop, and expect to revisit that budget.
  • A permission prompt that never returns. requestAccess blocks until the user answers, so streamlib dev would look hung. Never await it on the critical path, and name the terminal in the error — there's no "+" button on the Camera pane, so a user who never got a prompt can't add themselves.
  • One unexplained hang in Metal's shader cache between two processes of the same executable (1 in ~15 runs; a 6×3 stress didn't reproduce). Matters because every helper shares one sys.executable.
  • A re-sign trap that only fails on users' machines. Any strip/lipo step invalidates the signature. Must end in codesign -f -s -. Worth a CI assertion — the portability test currently skips silently on Mach-O rather than failing.
  • Never daemonise the engine, or the permission chain breaks and camera access silently dies.
  • Linking and first run are still unmeasured. Every measurement here stops at compile, or at a standalone probe.

One strategic note

KosmicKrisp — LunarG's Vulkan-on-Metal driver in Mesa — is MIT-licensed and fully Vulkan 1.3 CTS conformant, macOS 26+ on Apple Silicon, and already ships in the LunarG SDK beside MoltenVK. MoltenVK's own README calls itself non-conformant. That's the argument for bundling the Vulkan loader alongside MoltenVK rather than hard-wiring MoltenVK: ~0.3 MB extra buys you that migration path, plus validation layers as an opt-in.
